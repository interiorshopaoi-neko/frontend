# PRO MATCH — ロードマップ

> 最終更新：2026年5月16日（Phase52 完了時点）
> 優先度：S > A > B > C

---

## 考え方の前提

- **今は大規模リファクタより、実運用事故を減らす方が重要**
- 「壊れない」だけでなく「**毎日使いたくなる**」サービスを目指す
- 職人が毎日開く理由を作る → データが貯まるほど改善される構造を作る
- 新機能は「完璧に作る」より「まず動くものを出して判断する」

---

## S：直近で着手（実運用の安定化）

### 1. craftsmen 自動作成の保証

**目的：** 職人登録フロー（メール確認→ログイン）が完了したのに `craftsmen` 行が作られない問題を防ぐ。

**現状：**
- Phase49 で `ensure_craftsman_for_auth_user` RPC を実装
- 登録前の旧ユーザー（craftsman4/5 など）は手動で補完済み
- 新規登録は RPC 経由で自動作成される設計

**残るリスク：**
- RPC がコールされないパスで登録された場合の検知・補完手段がない
- 管理画面で「craftsmen 行がない auth ユーザー」を検出できると安心

**やること：**
- 管理ダッシュボードに「craftsmen 行なし職人リスト」の検出と補完ボタンを追加

---

### 2. 実運用事故の検知強化

**目的：** メールが届かない・通知が失敗するケースを早期発見する。

**やること：**
- 各通知 API の `ownerReason` / `applicantReason` を Vercel ログで定期確認する仕組みを整える
- `craftsman_id = null` の助っ人募集が増えないよう、新規投稿時にログイン必須チェックを強化

## 判断基準

新機能の優先度を決めるときは以下で判断する：

1. **実運用中の事故・トラブルを防ぐか？** → 最優先（S）
2. **職人の仕事が増えるか？** → S / A 優先
3. **職人が毎日開く理由になるか？** → A / B 優先
4. **依頼者のハードルが下がるか？** → A 優先
5. **DB 設計・法律・決済が絡むか？** → 慎重に C 以降
