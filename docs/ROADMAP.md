## お客様依頼フォームの設計思想（Phase57 以降）

- フォームは「部屋カルテ型」に寄せる：部屋ごとに工事内容・写真・希望が一体で見えること
- 初期表示はシンプル、詳細（状態・材料・写真）は折りたたみ内に格納。広さは常時表示（必須）
- クロスは「壁 / 天井 / 壁＋天井」として分離、床は「クッションフロア」として独立選択
- 「両方」という曖昧表示はお客様向けに廃止（内部 workType は互換維持）
- 動画は全体把握、写真は傷・詳細確認として役割を分ける
- 品番未定・情報未入力でも安心して送信できる設計を維持
- 将来的には roomMedia をDB正規化する（現状は meta JSONB に保存）

### 広さ・材料・アクセントの設計原則

- **広さは必須**：見積金額に直結するため必須化。ただし「不明」も許可し、離脱を防ぐ
- **材料希望（クロスのグレード）とアクセントクロスは別概念として分離**
  - 材料希望：量産 / 1000番・機能性 / まだ決まっていない（グレード・素材感）
  - アクセントクロス：一面だけ色/柄を変える・木目/石目調など（貼り方・演出）
  - 柄物はデザインの話、アクセントは配置の話 — 混在させない
- **状態に「穴」を追加**：クロス補修依頼で多い。「傷」と区別して職人が素早く判断できる
- **雰囲気カード（WALLPAPER_STYLES）は理想の空間イメージ**：アクセントとは別枠で選ぶ

### meta / 下書き保存の設計原則

- **wallWorkScope / floorWork が真の工事範囲**：`workType` は旧形式互換用としてのみ保持
  - `wallWorkScope`: `'wall' | 'ceiling' | 'wall_ceiling' | ''`
  - `floorWork`: `boolean`（クッションフロア ON/OFF）
  - 旧 `workType='両方'` は「壁クロス＋クッションフロア」の意味（天井なし）
- **localStorage draft には File/objectURL を保存しない**：復元時は `roomVideoFiles: [], roomImageFiles: []` で初期化
- **管理・職人側では requestMeta.ts の helper 経由で読む**：`getRoomWorkSummary()` が新旧両形式を処理
  - `hasCeilingWork()`: wallWorkScope / workType の両方をチェック
  - `getRoomWorkSummary()`: 「両方」は「クロス：壁 + 床：クッションフロア」に分解して表示
  - `getWallpaperAccentPreferences()`: `wallpaper_accent_preferences` を安全に取得
- **直接 `room.workType` を表示しない**：「両方」などの内部値が露出する

## 職人向け案件一覧の設計方針（Phase58 以降）

### 案件フィルター方針
- フィルターは 6 個程度に絞る：全て / 新着 / 急ぎ / 動画 / 写真 / 情報充実
- 細かい判断材料（天井あり・アクセント希望・材料未定・施工量）は現場レーダーのカード内チップで見せる
- 「クロス」「床」「天井あり」などの工事種別フィルターは不要（work_type を読めば分かる）
- 「今日・明日」は通常案件（estimate_requests）では preferred_date が曖昧なため使わない
- 急ぎフィルター：urgency === 'today' | 'tomorrow' | 'soon'、または timing テキストに「急ぎ・至急・なるべく早く」を含む
- 情報充実フィルター：動画あり + 写真あり、または roomMedia に動画/写真がある

### 新着案件の表示強化
- 24時間以内は `ring-2 ring-blue-400 shadow-blue-100` で枠強調
- 30分以内 → `🆕 NEW`（animate-pulse）、2時間以内 → `🔥 新着`、24時間以内 → `✨ 本日投稿`
- 並び順は純 created_at desc（動画あり優先でソートしない）
- 5日以上経過案件は `opacity-70` で弱く表示

### 新規案件通知設計（Phase59 以降）

**現状：**
- 全職人に一斉メール通知（距離・工種フィルターなし）

**将来ロードマップ：**

| ステップ | 内容 |
|---|---|
| Step 1 | 職人の対応エリア＋工種一致で通知対象を絞る |
| Step 2 | 距離計算（緯度経度）で近い職人を優先通知 |
| Step 3 | 急募案件だけ即時通知、通常案件はまとめ通知（通知疲れ防止） |

**設計方針：**
- 全員通知は避ける → マッチ精度が上がるほど応募率が上がる
- 詳細住所はマッチング前に開示しすぎない（セキュリティ配慮）
- 急募（urgency=today/tomorrow）は即時通知を優先
- 通常案件は 1 日 1 回まとめ通知も検討（将来）

**今回は通知 API は変更しない。**

### 動画/写真ライフサイクル（将来設計）

## 「現場判断OS」としての設計方針（Phase59 以降）

PRO MATCH 職人側 UX の基本思想。新機能追加・改修時はこの方針で判断する。

### 案件一覧は情報量より判断速度を優先

- 職人は 3 秒でスキップ or 詳細に進む判断をする
- カード内に詰め込みすぎない → 最重要情報を上に集める
- **表示優先順位：場所 → 工種 → 動画/写真 → 広さ/部屋数 → 急ぎ度 → 手取り目安**
- 難易度・材料希望・状態は現場レーダーで補足

### フィルターは 6 個程度まで

- 「全て / 新着 / 急ぎ / 動画 / 写真 / 情報充実」が基本セット
- 工事種別（クロス/床/天井）はフィルターではなくカード内チップで判断
- フィルターを増やすと選択疲れが起きる

### 詳細情報は現場レーダーで見せる

- 現場レーダー（SiteRadar.tsx）が職人の「現場判断補助」の役割
- チップは最大 6 個・難易度バッジ・情報充実度インジケーターを含む
- 動画/写真チップはカードのクイック情報チップと重複するが許容（異なるコンテキスト）

### 応募ボタンは詳細画面に集約

- 一覧カードには「詳しく見る →」のみ
- 応募 CTA は CraftsmanApplyPage に集約（誤タップ防止）
- 応募前に安心文言を表示（「送信だけで成約確定にはなりません」）

### 成約後も動画/写真/部屋情報を見返せる

- `readOnly: true` で CraftsmanApplyPage に遷移（応募フォームは非表示）
- 工事前の確認・施工範囲確認に使える
- 連絡先開示・施工前確認・工事完了報告は別フロー

### 案件管理ページは「今やること順」で並べる

- 成約直後の職人が最初にやること：現場確認 → 日程調整 → 施工前確認 → 完了報告
- 成約済みカードは「🎥 現場を確認する」を最上位 CTA にする（次の流れチップで①を強調）
- CTA 文言は「現場を確認する」に統一（「案件内容を見る」は使わない）
- 成約直後バナーは行動寄り文言（「⚡ 成約した案件があります」）
- 完了済みカードは過去ログ扱い — opacity 50 + 連絡先ボタンをアウトライン化
- 将来的に完了案件は「完了済み（N件）」として折りたたみ、現在進行中を最優先表示
- 将来的に「返信待ち」「日程未確定」「施工前確認未送信」などの軽量ステータスを検討
- 無料枠と紹介コードはセットで案内（「無料枠を増やす方法」として紹介コードを直下に）
- 現場ツールは便利機能として独立表示（案件カードより目立ちすぎない小さめカード）

### 完了後はメディア削除ライフサイクルを検討

- 工事完了後 30 日経過で元動画を削除候補
- サムネイル・テキスト情報は長期保持
- Storage コスト抑制と情報保全のバランスを取る

## 判断基準

新機能の優先度を決めるときは以下で判断する：

1. **実運用中の事故・トラブルを防ぐか？** → 最優先（S）
2. **職人の仕事が増えるか？** → S / A 優先
3. **職人が毎日開く理由になるか？** → A / B 優先
4. **依頼者のハードルが下がるか？** → A 優先
5. **DB 設計・法律・決済が絡むか？** → 慎重に C 以降
