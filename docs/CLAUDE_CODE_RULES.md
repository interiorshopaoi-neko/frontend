# PRO MATCH — Claude Code 実装ルール

> このファイルは Claude Code（AI）が毎回守るべきルールです。
> `docs/ai-rules.md` に加えて、Phase51/52 の事故を踏まえた運用ルールを記載します。

---

## セッション開始時の必須確認

**毎回、最初に必ず以下を実行・表示してから作業を始める。**

```bash
pwd                          # 現在の worktree
git branch --show-current    # 現在のブランチ
git log --oneline -3         # 直近のコミット
git status                   # 未コミット変更の確認
ls docs/                     # 既存の docs 構成
```

**なぜやるか：** 間違った worktree・ブランチで作業してしまうのを防ぐ。Claude Code はセッションをまたいで文脈を失うことがあるため。

---

## 推測で直さない

### NG
```
「たぶん full_name だろう」と思って直す
「前回と同じ構造のはずだ」と決め打ちで実装する
```

### OK
```
実際にファイルを Read して確認する
Supabase Studio や実レスポンスでデータを確認する
Vercel のログを確認して原因を特定してから直す
```

**なぜやるか：** Phase51 では「name vs full_name」「RLS による空配列」「ReferenceError」が**重なって**発生した。推測で進めると原因を誤診し、修正しても直らない。

---

## 実コード・実DB・実ログ・実レスポンスを確認する

問題が発生したら以下の順で確認する：

1. **ソースコードを Read** — 最新の実装を確認（記憶や要約に頼らない）
2. **実レスポンスを確認** — curl やブラウザ DevTools で実際の API 応答を見る
3. **Vercel ログを確認** — Function のログに `ownerReason` や `applicantReason` が出る
4. **Supabase Studio を確認** — テーブルに行が存在するか、RLS が意図通りか
5. **実際にメールが届くかテスト** — API が 200 OK でも届かないことがある

---

## 最小差分で実装する

- 変更するのは「必要なファイルだけ」
- 既存の動いている機能を変更しない
- 新しい依存パッケージを追加しない（明示的に依頼があった場合のみ）
- リファクタリングは依頼された場合のみ行う

**なぜやるか：** 変更範囲が広いほど、壊れる箇所が増える。「最小差分」文化は事故を減らす。

---

## 既存の成功済み機能を壊さない

変更を加える前に：
1. 変更対象ファイルを Read する
2. そのファイルに依存しているコンポーネントを確認する
3. 変更後に `npx tsc --noEmit` でエラーゼロを確認する
4. 変更後に `npm run build` でビルド成功を確認する

**特に注意が必要な箇所：**
- `useAuth.ts` — 大改造禁止。既存の認証フロー全体に影響する
- `BottomNav.tsx` — タブを増やさない
- Supabase RLS — 緩めるとセキュリティ影響が大きい

---

## RLS を安易に緩めない

問題が「anon からデータが見えない」であっても、最初にやることは：
1. SECURITY DEFINER RPC を作れないか検討する
2. authenticated ユーザーに絞れないか検討する
3. それでも必要なら → PII を含まない公開情報のみを anon SELECT に開ける

**絶対にやらないこと：**
```sql
-- ❌ craftsmen に anon SELECT を開けない
CREATE POLICY "craftsmen_anon_select_all" ON craftsmen
  FOR SELECT TO anon USING (true);
```

---

## API キーや秘密情報を docs や コードに書かない

- Supabase の URL・anon key・service_role key は `.env` や Vercel の環境変数で管理
- Resend API キーは Vercel の環境変数で管理
- docs ファイルにキーの値を書かない（masked でも書かない）
- コードには `process.env.SUPABASE_URL` のように環境変数経由でアクセスする

---

## tsc / build の確認

```bash
# TypeScript チェック（必須）
npx tsc --noEmit

# ビルド確認（デプロイ前必須）
npm run build
```

- 変更を終えたら必ずこの2つを実行する
- エラーがある場合は修正してから報告する

---

## 最後に必ず報告する

作業完了後、以下をまとめて報告する：

1. **変更したファイル一覧**（新規作成・更新・削除）
2. **何のためにどう変えたか**（専門用語だけでなく目的を書く）
3. **tsc / build の結果**（「0エラー」または「エラー内容」）
4. **残るリスク・未解決の問題**
5. **推奨コミットメッセージ**

## ユーザーへの説明方針

ユーザー（masato さん）は初心者ではないが、全ての技術用語が自明ではない。
以下を心がける：

| 説明の要素 | 内容 |
|---|---|
| **何のためにやるか** | 目的・背景を最初に書く |
| **何が変わるか** | 変更前→変更後の差分を明確にする |
| **どう確認するか** | 「このURL を開いて確認してください」など具体的に |
| **専門用語** | 初出時はカッコ内に一言で説明する |

**例（NG）：**
> RLS policy を anon role に付与しました。

**例（OK）：**
> データベースの「閲覧ルール（RLS）」を更新しました。
> これにより、ログインしていないユーザーでも職人の案件一覧が見えるようになります。
> `/craftsman/jobs` を開いてリストが表示されるか確認してください。

## 重要な禁止事項（ai-rules.md との統合）

| 禁止 | 理由 |
|---|---|
| `useAuth.ts` の大改造 | 既存認証フロー全体に影響する |
| anon へ craftsmen SELECT を直接開ける | 個人情報漏洩リスク |
| `onboarding@resend.dev` を from に使う | 職人宛メールが届かない |
| service_role key をフロントや公開コードに出す | セキュリティ事故 |
| BottomNav にタブを追加する | UX・認知負荷 |
| 大規模リファクタリング（依頼なし） | 最小差分文化 |
| Supabase テーブル構造の変更（依頼なし） | 影響範囲が大きい |
| tsc エラーが残ったままデプロイ | 本番クラッシュの原因 |
